The folders, from top to bottom

The Engine has one folder for each concern. A folder imports only from the folders below it. This keeps each file small and easy to find.

Three layers between a tool and the files

Toolbox and handlers (tools/)

The model asks for an action, for example "edit line 3". A handler turns the request into a call on the working copy.

How the Engine creates the working copy

One line in fix/attempt.py creates it. This happens once for each ticket, right after the workspace opens.

  1. workspace = context.repo_provider.open_workspace(ticket.repo)
  2. working_copy = WorkingCopy(workspace, settings)

The constructor copies no file. It stores the workspace and the settings. It makes two empty dictionaries: originals and current.

What "open a workspace" means

open_workspace(repo) is a method of the repo provider. It returns a new Workspace: a private checkout of the repository. Each ticket gets its own. A Failed Fix leaves nothing behind, because the Engine never commits that checkout.

In the tests, FakeRepoProvider.open_workspace runs git clone of a local repository into clone/<n>/<repo>. The number n is new for each call.

What happens when the model edits a file

  1. Check the path. Refuse workflows, lockfiles, secret files and paths outside the repository.
  2. Read the current text. If the file does not exist, refuse: new files are not allowed.
  3. If the old text is not in the file, refuse.
  4. If the new text leaves the file empty or only blank, refuse: deletions are not allowed.
  5. Count the changed lines of all edited files. If the count is more than the diff limit, refuse.
  6. Write the new text to the workspace now. Update current. Keep the first text in originals.

A refused edit changes nothing. At finish, the Engine runs the final checks. The change must not be empty. It must not be over the limit. Each edited file must still parse.

What happens to one tool call

The class Toolbox in tools/toolbox.py runs these four steps for every call. A tool never raises an error. A wrong call gives text that starts with Error: or Refused:.

1 Find the tool by name→ 2 Check the arguments with a pydantic model→ 3 Call the handler→ 4 Cut the result to 8 KB

The handlers are in tools/handlers/. Each has the same shape: handler(args, working_copy, settings) returns text.

edit_file

Arguments
path, old, new
What it does
Asks the working copy to replace the first old text with new.
Result
Edit applied. or Refused: …
File
handlers/edit_file.py

read_file

Arguments
path, start_line (1 or more)
What it does
Reads the current text of one file. Returns up to 300 lines from start_line. If more lines exist, it adds the note to narrow the request.
Refuses
Secret files and paths outside the repository.
File
handlers/read_file.py

search

Arguments
pattern (a regular expression)
What it does
Reads every file that the model may read. Returns up to 50 lines as path:line:text. It skips secret files and binary files.
Errors
A pattern that is not a valid regular expression.
File
handlers/search.py

list_dir

Arguments
path (default .)
What it does
Lists the entries of one folder. A folder name ends with /. It hides secret files.
Refuses
A path outside the repository.
File
handlers/list_dir.py

finish

Arguments
summary
What it does
It has no handler file. fix/conversation.py sees the name and ends the loop. The Engine then runs the final checks and publishes.
File
fix/conversation.py

Two helpers

handlers/readable.py
readable_path checks one path. readable_files lists the files that the model may read.
tools/result_cap.py
Cuts a long result and adds the note: "The result is incomplete. Make the request narrower."
